THOR — independent super resolution + frame generation product objective
User objective: continue until an actually usable DLSS-like product exists.
This goal is NOT satisfied by loading a layer, counting submissions, a demo,
same-resolution sharpening, or recommending another app's frame generator.

Required end state (all remain required until supported by evidence):
1. One independent controller/engine on AYN Thor. No external FG app or Lossless
   DLL dependency. Emulator/game remains the source, not the FG implementation.
2. Real lower-render-resolution -> display-resolution reconstruction in a game,
   with an independently implemented/integrated SR algorithm. Record the input
   and output sizes and demonstrate useful quality/performance against native
   rendering and simple bilinear. Do not label same-size sharpening as DLSS.
3. Real independently generated intermediate frames, paced and displayed.
   Quantify source cadence, generated/rejected frames, actual presentation,
   compute cost, added latency, and source-game performance separately.
4. Rapid cuts/fast camera movement: reject unreliable interpolation, reset
   temporal history, and recover without old-scene warping or mixed scenes.
   Validate on adversarial fixtures AND relevant gameplay, not one color cut.
5. Preserve game timing/input and HUD readability. No capture feedback loops.
   Document and test occlusion/disocclusion, thin details and scene transitions.
6. Cover the user's emulator use, including DroidDeck. Track each installed
   emulator, backend and custom-loader path separately. Do not infer universal
   compatibility from a startup test or one Vulkan target. OpenGL ES remains
   outstanding until a working path has been built and verified.
7. Installable, recoverable app/configuration, clear activation/status, resource
   cleanup, resize/restart handling and a reliable off/restore action. Defaults
   and status must represent actual runtime state.
8. Sustained testing on the actual Thor: compare quality, FPS, thermal behavior
   and latency with FG/SR off, SR-only and SR+FG. Mere compilation/validation or
   a higher counter does not prove the user goal complete.
9. User-requested automatic mode: recognize installed emulator/game candidates,
   permit explicit package opt-in/out, inject early enough for a normal launcher
   launch, preserve boot/update configuration and a working off action. Scope
   injection by UID/package; foreground HUD must remain truthful and disappear
   on ordinary apps. Do not globally force a Vulkan layer or silently kill games.

NVIDIA's proprietary binary/model is not an implementation option on Adreno.
The requested equivalent function/quality remains the target; names and claims
must accurately distinguish neural/temporal/spatial SR and measured results.

Current verified baseline and gaps:
- Android Vulkan layer and scoped Zygisk bootstrap run in DroidDeck0.5.0.
- Motion remains a coarse small-window block search. Version0.2 now rejects
  cut/unreliable pairs before acquiring/presenting a generated frame, preserving
  the original image and holding off for2pairs.21GPU fixtures pass; gameplay
  quality and pacing are not yet demonstrated by those fixtures.
- Version0.3 adds a real low-resolution application-blit -> display SGSR1 path,
  with per-command resources, compute-state restoration and source-crop support.
  External-layer output matched independent SGSR reference pixels in3frames;
  an SR-off negative control differed as expected. In-game low-res SR benefit
  and quality are still unverified, so the game requirement remains outstanding.
- Three per-pair queue-idle waits have been replaced with submission fences;
  GPU timestamps now separate input/quality/interpolation and output-copy cost.
  CPU quality readback still waits roughly7–8ms in the synthetic display-sized
  fixture. Opportunistic extra acquisition and synchronous readback remain;
  async scheduling/proxy presentation and display-budget handling are required.
- No gameplay quality, end-to-end latency or sustained-benefit proof exists.
- Version0.5 also ran actual Castlevania intro/cutscene/dialogue through the
  DroidDeck compositor with its own effects/upscaler disabled. All274 retained
  valid telemetry windows reported Thor spatial SR1280x720->1920x1080; median
  source-present22.34FPS, display-timing40.28FPS. Input FG GPU median6.724ms and
  CPU quality wait19.034ms still expose the blocking path. These measurements
  do not establish traversal/combat quality, source-performance benefit or
  input latency. The original emulator effects and game save were restored.
- A movable HUD uses native per-PID/boot-clock telemetry with stale-data expiry.
  It shows only source and post-FG FPS. Output uses valid presentation timestamps
  when available, otherwise an explicitly marked estimate; detailed SR status
  remains in the controller app.
- Version0.4 automatic injection was verified after reboot in PPSSPP and at
  DroidDeck application binding. A non-debuggable sample, with the manual target
  still pointing at DroidDeck, displayed about60FPS from30FPS and real spatial
  SR. An automatic+validation session survived Home/recreation, two swapchains
  and113s of telemetry without captured validation errors. These are not proof
  of in-game quality/performance or universal emulator compatibility.
- Thor_DLSS_Source.zip was reviewed separately. Its duplicate-present wrapper
  and disconnected shaders do not supply the missing FG/SR engine. See the
  source review; do not merge that wrapper as a shortcut to product completion.

Next evidence-driven work:
A. Extend the passing cut/fast-motion fixtures to real gameplay, HUD/occlusion,
   high-frequency detail and reliable optical flow over larger motion ranges.
B. Evaluate a mobile neural SR model/runtime and an actual low-resolution source
   path; retain full scope rather than calling a spatial filter the end product.
C. Replace the blocking presenter and coarse flow as measurements require.
D. Version0.5 pins each engine binary in an immutable signed runtime APK. A
   controller-update regression was reproduced with the legacy path and passed
   with the pinned path in the same DroidDeck PID. Bootstrap0.3 bypasses a missing
   runtime before automatic injection. Keep old runtimes while bound processes
   may reference them; automatic reclamation remains unimplemented. Bootstrap3
   boot recovery and a missing-runtime PPSSPP startup were verified on the Thor.
